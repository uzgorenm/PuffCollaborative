# Runner contract

This document supplements [the coordination contract](coordination-contract.md). The coordinator owns project access, instruction order, authoritative Run state, approvals, and the project event feed. The runner accepts an authorized command, uses the bound OpenCode Session and workspace, and reports what it observed. The runner's SQLite records track local execution and callback delivery; they do not replace coordinator records.

## Pinned implementation and deployment

The repository pins OpenCode `1.18.33`, Bun `1.3.14`, and Effect `4.0.0-beta.83`. The MVP runs coordinator and runner in one server process with the existing `Database.Service`. Use embedded `SessionV2.Service`, `SessionExecution.Service`, `LocationServiceMap`, and the V2 Session event stream. Do not launch an additional OpenCode server or model loop. `SessionV2.prompt` durably admits a stable message ID; `resume: false` leaves scheduling to R3 after the observer is installed. `SessionExecution.wake` coalesces work for an active Session and runs different Sessions concurrently. A process crash does not authorize automatic replay of model work.

The coordinator's `RunnerPort` is already defined in `packages/core/src/coordination/contracts.ts`; its gateway and authentication remain coordinator owned. The real adapter is supplied through the existing `coordinationLayer({ runnerPort, sessionBinding, projectAdmission })` ports. R1 provides the runner side of those ports and requests any central composition edit from the coordinator owner. Development mock mode remains an explicit fixture path. Production enablement requires a configured individual identity roster, trusted project admission, real Session binding, and real runner port. Missing components return 503 on coordination routes.

## Identity and trusted binding

`projectId` is an OpenCode Project ID. A coordinator `threadId` has one existing `sessionId` and one original `workerId`; the runner records one persistent `workspaceId` and canonical directory for that Thread. `runId` identifies one coordinator Run and is the runner's start-request identity. `runnerMessageId` is the OpenCode `msg_` ID generated by the coordinator at submission and remains fixed across retries. The runner deduplicates by `runId` and the complete immutable command payload; changed reuse conflicts. The coordinator Run has an `attempt` counter, but `RunnerCommand` has no attempt field. R4 reads that counter from trusted Run storage for diagnostics; it is not part of start identity and a counter change never authorizes a second prompt. `executionOwner` binds the original worker and instance and is checked against R12's configured identity. `runtimeId` identifies the embedded runtime attached to that instance; it is not a Session ID. A new Run on the same Thread reuses its workspace and Session.

`RunnerCommand` contains `runId`, `threadId`, `sessionId`, `executionOwner`, `runnerMessageId`, and text. It does **not** contain `projectId` or `attempt`, and this supplement does not add either field to the coordinator protocol. R4 obtains project and current attempt from the coordinator's trusted Run, Instruction, and Thread records, checks their cross references and exact command text, then verifies the Session's project and location. R12 checks the configured worker/instance credential against `executionOwner`. A changed command for an existing `runId` is a conflict before any workspace or prompt side effect. Neither a browser value nor the command itself is authoritative workspace metadata.

The runner's thread binding stores `threadId`, `projectId`, `sessionId`, `workerId`, `workspaceId`, and canonical directory. R2 and R4 create it only after verifying the actual workspace and Session. R4 supplies the coordinator's `SessionBinding.resolve(sessionId)` from that trusted state. A Session already bound to another Thread, a workspace outside the project, a worker mismatch, or a changed directory fails closed. An existing Session without an isolated workspace needs an explicit migration decision; silently starting a fresh Session would break continuity. R12 also checks the canonical directory against approved roots before R3 attaches the runtime.

## Port and module calls

R1's `composition.ts` implements the coordinator's current `RunnerPort` without changing its signature:

| Coordinator call | Runner path | Result |
| --- | --- | --- |
| `start(RunnerCommand)` | R1 hands the command to R5. R5 calls R12 scope validation, persists acceptance, prepares R2 workspace/R3 runtime/R4 Session, installs R6 observation, admits the exact prompt, and asks R3 to wake the Session. | Return `{ messageId: runnerMessageId }` after durable admission and scheduling. Execution and reporting continue asynchronously. |
| `interrupt({ runId, sessionId })` | R9 verifies the bound Run and Session, asks R5 to record cancellation intent, then calls R3 interrupt | An idle interrupt is a no-op; only R5 changes the local phase. |
| `resolveApproval({ approvalId, decisionId, runId, sessionId, decision })` | R8 verifies exact pending native request, Run and tool call; R5 records decision identity; R8 calls native permission reply | Exact decision retry has one effect; conflicting or ambiguous decisions fail closed. |
| `reconcile(runnerMessageId)` | R10 reads local execution, durable `session_input`, and current runtime observations | Return only `missing`, `admitted`, `running`, or `terminal` when supported by evidence. Unknown execution remains held for reconciliation. |

The in-process callback path calls the coordinator's existing `Runner.report({ principal, runId, callbackId, callback })` through R7, using R12's validated principal. R3 attaches the embedded runtime to a verified workspace, exposes its runtime ID and health, bounds readiness waiting, owns observer fibers and shutdown, and sends process/drain failure evidence to R5. After R10's startup reconciliation, R3 owns a bounded periodic call to R7's `drainDue(limit)` and stops it on shutdown. It does not spawn a second OpenCode server. A separate worker deployment would need authenticated transport, durable worker placement, and a new recovery design; it is outside this MVP.

## Local phases and persistence

R5 alone moves the local execution through `accepted → prepared → admitted → running → waiting_approval → running → terminal`, with `cancelling` and `recovery_required` branches. R5 also orchestrates one complete authorized turn. R3's `watch` waits for R6 to register its listener and replay durable history before prompt submission. R5 records submission intent, then calls `SessionV2.prompt` with `runnerMessageId`, `delivery: "queue"`, and `resume: false`. An exact retry returns the same admission; changed text, Session, or delivery conflicts. R3 wakes execution only after the observer is ready. A correlated settled step is not terminal proof: R5 asks R3 to wait for the exact Session drain and scoped tools to become idle before a terminal transition. A timeout leaves the Run occupied for recovery. These local phases are observations. The coordinator's `queued/reserved/running/waiting_approval/cancelling/recovery_required/completed/failed/cancelled` state remains authoritative and changes only through its `Queue.transition` and authenticated callback path. R5 must compare the expected local phase and keep terminal phases immutable. Other modules provide evidence or request a transition through R5's interface.

The runner foundation migration provides a one-to-one Thread/workspace/Session binding and an execution row keyed by `runId` with the exact command and observed phase. The execution row also records R3's last abort-delivery and stop observations through R5; R9 never writes it directly. R5 stores R11's complete pre-run artifact baseline in the execution row during `prepared`, before prompt admission. R7 owns the outbound callback table and its migration. Each row stores `run_id`, `callback_id`, a stable `producer_key` unique per Run, a per-Run ordinal, exact callback JSON, optional Session source sequence, trusted execution owner, creation and acknowledgment times, retry count and next retry time, and a permanent-failure/last-error marker. R8 owns a fourth table that maps `run_id`, `session_id`, native `permission_request_id`, `tool_call_id`, and coordinator `approval_id`, plus the stable decision ID and delivery status. R1 registers both feature migrations without changing their mapping or retry rules. R5 commits a phase change and its callback drafts in one SQLite transaction by calling R7's `append(tx, drafts)` inside that transaction. R7 assigns durable callback IDs and ordinals there, then updates acknowledgment fields after the coordinator has committed each callback. No outbound callback runs inside a SQLite transaction. Unsent intents survive a crash.

## Reports and ordering

R6 normalizes and correlates OpenCode observations to the admitted Run. R7 turns those observations and R5 phase decisions into the coordinator's existing `RunnerCallback` union. Activity uses `kind: "activity"` with `state: "running" | "waiting_approval"` and one `run.tool`, `run.output`, `run.workspace`, or `run.diff` value. State reports use `kind: "state"`, `expectedState`, and `nextState`; entering `waiting_approval` includes both `approvalId` and `toolCallId`. Text and summaries are capped at 8,000 characters. Raw tool inputs, complete output, patches, file contents, and secrets are not copied into coordinator activity.

Every outbound row stores the exact callback payload, stable `callbackId`, local ordinal, and source Session aggregate sequence where one exists. R7's `append(tx, drafts)` is the only callback insertion path; R5 calls it inside the same transaction as the local phase change. R7 sends callbacks for a Run in ordinal order. It sends the next only after the coordinator acknowledges the previous one. A successful `Runner.report` response means the coordinator committed that callback; a lost response leaves the row pending and R7 retries the same ID and payload. The coordinator treats an exact retry as a no-op and changed data for the ID as a conflict. A terminal callback is last and is sent only after earlier activity and approval reports are acknowledged and the observed Session drain has settled. A prompt admission or HTTP response is not proof of model completion. R7 must distinguish source event order from project event sequence.

The shared coordinator `RunnerCallback` has no failure-detail field. R7 may send a bounded `run.output` summary before a `failed` state report, while the full error remains in OpenCode. Adding a richer result payload requires coordinator agreement.

R12 provides R7 with `principal(executionOwner)` and checks that the configured worker and instance match; R7 cannot copy the unvalidated owner from the command into a callback. R12's artifact policy receives a canonical path and returns a safe reference or rejection before R11 exposes it. Its redaction interface removes configured sensitive content from summaries and logs. Tool processes currently inherit host authority and the runtime environment in pinned OpenCode, so this embedded mode supports trusted local workers only until a stronger OS/container boundary and sanitized tool environment are verified. An OpenCode permission rule is not a filesystem sandbox.

## Approval and cancellation boundaries

Native `PermissionV2` requests are process local. R6 passes a correlated permission observation to R8, which persists the exact Run/Session/request/tool/approval mapping before asking R5 to enter `waiting_approval`. R8 includes a bounded, R12-redacted `toolName` and `summary`; R5 emits that `run.tool` activity before the waiting-approval state callback, which includes the mapped `approvalId` and `toolCallId`. `RunnerPort.resolveApproval` is called only by the in-process coordinator adapter after member authentication and a durable decision. Before native reply, R8 also reads back the decided coordinator Approval through the trusted `ApprovalAuthority.verifyDecision` port and checks its Run, decision ID, and decision against the command and local mapping. R8 then passes the native action result to R5 for the next phase and R7 report. `approve` maps to native `once`, never `always`. In pinned OpenCode, native `reject` also rejects every pending permission in that Session. R8 may use it only when the target request is the sole pending permission; if more are pending, it reports a conflict and leaves the coordinator decision pending for reconciliation. R8 invalidates pending mappings when R5/R9 confirms cancellation or terminal completion. After a process restart, a missing native request is unknown rather than successful delivery. The coordinator's approval is a tool approval; it does not authorize redirection of another Session's work.

Cancellation first persists the coordinator request. R9 validates the exact Run/Session binding, asks R5 to record local intent, and asks R3 to interrupt the active process-local ownership chain. R3 returns abort delivery (`acknowledged`, `unknown`, or `not_delivered`) separately from stop state (`stopped`, `already_idle`, or `uncertain`), with runtime and Session IDs, and exposes an inspection of active drain and tools. R9 passes that result to R5 for local persistence. R9 reports `cancelled` only when the exact drain and scoped tools are confirmed stopped; an acknowledged abort alone is insufficient. If interruption is uncertain, the Run stays occupied and R10 reconciles it. Cancellation does not delete the persistent workspace or Session.

R11 records a pre-run Git/workspace baseline and reports added, modified, deleted, renamed, untracked, binary, oversized, and unavailable/truncated cases separately. It marks paths already dirty before this Run so they are not attributed to the new turn without evidence. The report carries project, Thread, and Run identity and bounded path/patch metadata. R5 saves it in the local execution row with the terminal transition. R12's `SecurityPolicy.artifact` filters each canonical path and reference; `redact` applies to any summary exposed to the coordinator. Until a retrievable diff reference is wired, R11 keeps `run.diff` activity empty rather than reporting a reference the coordinator cannot resolve.

## Recovery and acceptance

On restart, R10 scans accepted or active local rows and pending callback rows, then reconciles each `runnerMessageId` with durable `session_input` and the original Session. It may re-admit an exact input when durable evidence says it is missing and the coordinator still owns the reservation. It must not replay a provider turn merely because the process died, a lease expired, or a callback response was lost. A Run with ambiguous external execution remains `recovery_required` until an operator or a later durable observation resolves it. Native pending tool permissions are not restored across process restart; R8 fails closed there.

R13 records source review, component fixtures, integrated embedded OpenCode execution, and real authenticated coordinator delivery separately. The runner feature is not complete on fixture evidence alone. For the hackathon acceptance work, use `docs/hackathon/progress-checklist.md` and the named workflows in `docs/hackathon/acceptance-workflows.md`. The informational awareness path in integration gate G0 is a separate coordinator contract decision; this Run port must not be repurposed into an unapproved context-injection command.
