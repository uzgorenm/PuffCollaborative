# Active Session awareness handoff

`SessionAwareness.admit` in `packages/core/src/session/awareness.ts` is the narrow runtime consumer for a **validated informational finding**. The coordinator supplies a stable `msg_` message ID, the target's existing Session ID, project ID and Location, and the source Session/event/revision, report ID, author ID and finding. It must resolve the target Thread's original worker from trusted storage and authorize that worker before calling this adapter. The V2 Session record contains project and Location but no worker identity, so this module can check the former and cannot independently certify the latter.

The coordinator must also validate project sharing, source references and revisions, target consent, note content, and redirection authority before the call. This adapter does not accept a coordination Run or reserve new work. In particular, tool approval is not approval for a cross-Session redirect.

On admission, the adapter checks that the existing Session matches the trusted project and Location. It records the attribution and source references in the exact prompt text and calls `SessionV2.prompt` with the supplied message ID and `delivery: "steer"`. The call durably admits one `session_input` before the existing `SessionExecution.wake(sessionID)` schedules work. A retry with the same ID and exact content returns the same `admittedSeq`; changed content, target Session or delivery conflicts. The active Session runner waits for its current provider/tool turn to settle, then promotes the input into the visible transcript before its next provider turn. It does not interrupt a tool or create another runner.

`admit` returns `sessionID`, `messageID`, `admittedSeq`, optional `promotedSeq`, and `activeObserved`. The last field is a process-local snapshot taken just before admission; it is useful for a timeline but does not prove the Session remained active through the commit. `SessionAwareness.receipt({ sessionID, messageID })` reads the durable `session_input`: `promotedSeq` is absent while pending and present after transcript promotion. Keep admission, promotion, and the target agent's actual use as separate states. A returned HTTP response or a coordination Run state alone proves neither promotion nor use.

The focused deterministic integration case in `packages/core/test/session-runner.test.ts` holds B's provider stream open, verifies that B's Session is active before the note, admits the same attributed note twice, observes one pending input, releases the provider turn, and checks one transcript promotion plus one subsequent provider request containing the source references. It also checks mismatched Location and changed-retry rejection. The provider is a controlled test stream, so this is runtime evidence for safe admission/promotion, not a live WF02 Flower report or proof that a model used the finding. WF02's full pass still needs a real A event, validated Flower result, coordinator delivery, B's concrete response, and the active-turn timeline. WF04 still needs end-to-end lost-acknowledgment and feedback-loop tests; WF07 remains at the coordinator validation boundary.
