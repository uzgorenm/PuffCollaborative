# Coordination runner

`RunnerAdapter.make` connects the coordination services to the execution port. It asks the queue to reserve the next instruction, resolves the Thread's Session ID through access control, and sends a start command after the reservation commits. The command carries the Run ID, stable runner message ID, and worker instance that owns execution.

The execution port must deduplicate start commands by Run ID and reject a changed command for the same ID. A response can be lost after the runner accepts a start. Server retries keep the original Run ID and message ID, but retries alone do not guarantee exactly one external execution. Each runner claim checks pending deliveries first. `recoverPending` checks the runner's recorded message ID before resending a reserved command. It also retries a Run in `recovery_required` if no start was confirmed and reconciliation says the message is missing. Other uncertain runs remain occupied. Recovery retries an interrupt for a Run in `cancelling` and replays pending approval decisions with their original decision IDs. The port must also deduplicate those control commands. A network failure leaves the reservation occupied. Only a confirmed terminal callback can release it.

Browser cancellation and approval decisions go through member authorization. Runner callbacks use a separate runner identity bound to the Run's worker and instance. The adapter checks that identity before passing a callback to the queue. The queue owns lifecycle transitions and callback deduplication. Output, tool status, workspace references, and diff references use the shared durable event path. Full tool inputs, file contents, and patches stay with the OpenCode Session.

The approval projection lives in `../approval`. The queue invokes its `requested` method inside the same event transaction as the transition to `waiting_approval`. Claims and new decisions require the Run to remain in that state. A member decision writes the decision and a pending delivery marker with one event. The adapter forwards the stable decision ID outside that transaction, then records delivery. If forwarding fails, the pending decision remains available for recovery.

The mock port in `mock.ts` can stream activity, delay steps, wait for approval, fail, cancel, emit duplicate callbacks, lose a start response, and disconnect. Its start and approval commands deduplicate by stable IDs. The adapter tests use mocked access, queue, and approval storage. The approval test uses real SQLite and the shared event journal with fixture access and queue lookups. The integration test runs the real queue and approval projection against SQLite and the event journal, with fixture access and the mock execution port. These tests do not verify execution through OpenCode.
